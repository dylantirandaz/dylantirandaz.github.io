Emergent topography: what language models think Earth looks like, in 3D

Epistemic status: rough draft. Land/water is checked against a real map; elevation isn't (I didn't fetch elevation data). One seed, one query order, no error bars.

Background

Henry (2025) asked different models “Land or Water?” one lat/lon point at a time, took first-token logprobs, and turned them into maps. Small models said land everywhere; real geography appeared as models grew. I replicated that and added elevation: four yes/no questions per point (above 3000m, above 1000m, below −1000m, below −4000m), combined into elevation bands and 3D globes.

Method

Grid

Points are cell centers on a 4° lat/lon grid (90×45 = 4,050 cells). An earlier 8° test run used 990 cells and stops at 82°N, since 180 isn't divisible by 8. Each cell is a separate API call. The model never sees a map, nearby cells, or its earlier answers, so every answer comes from memory. Query order is shuffled each run (seed 3).

Prompts

Land/water:
Location: 45.0° N, 90.0° W
If this location is over land, say 'Land'. If this location is over water, say 'Water'. Reply with only the word.

Threshold T (example T=+1000):
Location: 45.0° N, 90.0° W
If this location is above 1000 meters elevation, say 'Yes'. Otherwise say 'No'. Reply with only the word.

These are the exact prompts. Negative thresholds say “below N meters elevation (i.e. deeper ocean than Nm)” instead. Coordinates must come first: with the instruction first, the Ollama chat template makes Qwen2.5 answer Land 96.5% of the time (accuracy 0.371); with coordinates first, the oceans come back with confident answers. Raw completions without the template behave like coordinates-first, so the problem seems to be the template combined with prompt order, not the wording.

Readout

Temperature is 0 everywhere. Local models: top 15 first-token logprobs, softmaxed over the two answer words, matching prefixes when a word splits into several tokens. Frontier APIs don't return logprobs, so their answers are a plain 0 or 1 from the text; answers I can't parse count as missing, not guessed. Frontier reasoning is at each model's lowest level (Astra: minimal, ~12 thinking tokens; Opus: minimal, ~95; Fable: low, ~0), since more reasoning cost several times as much without changing answers on test cells.

Models

Local, via Ollama at 4-bit: Qwen2.5-7B-Instruct, Qwen3-8B, Llama3.1-8B, Gemma2-9B. Frontier, via OpenRouter: GPT-6-Astra, Claude-Fable-5.1, Claude-Opus-5.5. Qwen3-8B failed: its OpenAI-compatible endpoint gave no usable logprobs in my setup (its thinking block got in the way), and its native API gave a noisy, mostly-land map. I keep it as a negative result, shown only where its output was readable (Gallery).

Scoring

The real map is Natural Earth's 110m land outlines on the same grid. Land share on the 4° grid: 0.332 by cell, ~0.29 by area. I report accuracy (land if P>0.5) and AUC. For elevation, I rely on band counts, landmark checks (Mechanism), and agreement between models.

Mechanism

Small models know the facts but fail all six landmark tests given as coordinates, including Everest, the Altiplano, and the Mariana Trench. Astra and Opus pass all six; Fable passes four (one explanation, one blank).

My take: every model can look up facts by name, but 7–9B models only place a coordinate within ~1,000 km. That's enough for continents, not elevation. Frontier models place coordinates precisely. Llama refuses where Qwen2.5 makes something up, so handling doubt is separate from knowing facts.

Limitations

  1. The 110m map misses small islands and exact coastlines, so some model “errors” are map errors.
  2. The lat/lon grid over-counts the poles, equally for every model.
  3. Frontier answers are only 0 or 1, so they lose the confidence that logprobs keep.
  4. A 4° cell can hold both peaks and valleys. The landmark tests help but don't fully fix this.
  5. Fable's scores skip cells where it explained instead of answering, which skews them.

Cost

Local: ~150k queries on Apple Silicon, free. Frontier: ~60k queries, ~$200 on OpenRouter. About two days in the background, mostly waiting on APIs.
